# A/B-эксперименты

Эксперимент сравнивает долю пользователей, совершивших целевое действие,
в контрольном и тестовом вариантах. [A/B-флаг](feature-flags.md) назначает
варианты, API собирает показы и конверсии, а сервис статистики сравнивает группы.
Полный сценарий с запросами и переносом идентификаторов между шагами есть
в [демо](demo.md).

## Подготовка и жизненный цикл

Создайте A/B-флаг с двумя вариантами, например `A` и `B`, и задайте веса.
Для расчёта требуются ровно два разных варианта. Контрольным считается `control`,
а при его отсутствии — `A`. Используйте один из этих ключей для контроля и
другой ключ, например `B`, для тестовой группы.

`POST /api/experiments` создаёт черновик. Передайте UUID флага в `flag_id`,
уникальное имя в `name` и название целевого события в `primary_metric`, например
`purchase`. `alpha` задаёт порог значимости и по умолчанию равен `0.05`.
Необязательный `min_sample_size` задаёт минимум участников в каждой группе.
API позволяет запустить эксперимент до проверки набора вариантов. Проверьте
конфигурацию и включите флаг, чтобы `/resolve` мог назначать варианты.

| __Статус__ | __Допустимый переход__ | __Поведение__ |
|---|---|---|
| __`draft`__ | `running` | Параметры можно изменить, черновик можно удалить. |
| __`running`__ | `paused`, `completed`, `stopped` | `/resolve` может назначать варианты, API принимает связанные события, доступны ручной и плановый расчёты. |
| __`paused`__ | `running`, `completed`, `stopped` | Новые назначения и приём связанных событий приостановлены. Ручной пересчёт сохранённых данных доступен. |
| __`completed`, `stopped`__ | Конечные состояния | Сохранённые результаты и отчёты доступны. Новые назначения и пересчёт прекращаются. |

Для перехода отправьте `PATCH /api/experiments/{experiment_id}` с отдельным
телом `{"status":"running"}` или другим допустимым статусом. Первый запуск
заполняет `start_date`, переход в конечное состояние — `end_date`. Запуск и
пауза занимают единственный активный слот на флаге. Повтор текущего статуса
не меняет состояние. Переход в конечный статус не запускает финальный расчёт,
поэтому сохраните итоговый снимок, пока эксперимент `running` или `paused`.

## Как связываются показы и конверсии:

1. `POST /resolve` назначает вариант и сохраняет `impression`. Сохраните
   `user_id`, `flag_key`, `experiment_id` и `variant` из ответа.
2. Когда участник совершит целевое действие, отправьте `POST /api/events/single`
   с `event_type: conversion`. Передайте тот же `user_id`, `flag_key`,
   `experiment_id` и назначенный `variant` в поле `variant_key`. В `event_name`
   передайте значение `primary_metric`.
3. При пересчёте сервис берёт первый показ и последнюю подходящую конверсию
   участника в его варианте. Конверсия засчитывается, если её время не раньше
   первого показа. Повторные показы или конверсии не увеличивают счётчики
   участников. Конверсия без показа не попадает в расчёт, а события одного
   пользователя в разных вариантах вызывают конфликт `409` при пересчёте.

Время можно передать в `timestamp`. По умолчанию API подставляет текущее
время UTC. При приёме связанного события API проверяет, что эксперимент
запущен, `flag_key` соответствует эксперименту, а вариант принадлежит флагу.
Для статистики важны участник и факт целевого действия. Числовое поле `value`
не суммируется, а `click` и `custom` в расчёт конверсии не входят.

## Расчёт и чтение результата

`POST /api/experiments/{experiment_id}/results` синхронно пересчитывает и
заменяет последний снимок в PostgreSQL. В расчёт входят события из MongoDB
независимо от `processed` и компактные данные участников, сохранённые при
очистке старых событий. `GET` на том же маршруте возвращает сохранённый
снимок, до первого расчёта — пустой список. Beat ставит задачу планового
пересчёта запущенных экспериментов каждые 30 минут.

Доля конверсии группы равна числу сконвертировавшихся участников, делённому
на число участников с показом. Эффект считается как доля тестовой группы
минус доля контрольной. Равенство долей проверяется двусторонним z-тестом с
объединённой оценкой доли. Для разницы сервис рассчитывает приближённый
доверительный интервал уровня `1 − alpha` с отдельными оценками долей групп.

| __Поле__ | __Как читать__ |
|---|---|
| __`sample_size`, `conversions`, `conversion_rate`__ | Участники с показом, участники с целевой конверсией и их доля. При нулевой выборке API сохраняет `conversion_rate: 0.0`, а шаблон показывает отсутствие данных. |
| __`enough_data`__ | В каждой группе нужно минимум пять конверсий и пять участников без конверсии. Если задан `min_sample_size`, его должна набрать каждая группа. |
| __`z_statistic`, `p_value`__ | Z-статистика измеряет разницу в единицах её стандартной ошибки. `p_value` — вероятность получить столь же или более экстремальную статистику при равных долях. |
| __`confidence_interval_lower`, `confidence_interval_upper`__ | Границы приближённого интервала для разницы долей. `0.10` соответствует 10 процентным пунктам. |
| __`is_significant`__ | Равно `true` при достаточных данных и `p_value < alpha`. Направление эффекта видно по разнице долей. |

Если данных недостаточно, счётчики всё равно доступны, а Z-статистика,
`p_value` и границы интервала равны `null`. Статистика сравнения общая для
обеих строк результата. Например, при `10/100` в контроле и `30/100` в тесте
с `alpha = 0.05` и `min_sample_size = 50` эффект составляет `+20` процентных
пунктов, `p_value ≈ 0.000407`, а 95%-й интервал — примерно от `+9.3` до
`+30.7` процентных пункта. При чтении результата учитывайте размер эффекта
и интервал. Плановые пересчёты показывают, как меняются данные, а порог
значимости применяется к каждому снимку отдельно, без поправки за повторные проверки.

## Шаблонные и LLM-отчёты

Оба отчёта используют уже рассчитанный снимок. Пока подходящего снимка нет,
запрос отчёта возвращает `409`. Префикс маршрутов ниже —
`/api/experiments/{experiment_id}`.

| __Способ__ | __Что получает клиент__ |
|---|---|
| __`GET /template/reports`__ | Готовый шаблон с метриками и кратким выводом. Формируется сразу, без Celery, внешнего API и записи в историю. |
| __`POST /llm/reports`__ | Ответ `202` с ID задания. Сервис сохраняет входные метрики и ставит задачу Celery. Повтор с тем же снимком возвращает существующее задание, пока оно в `pending`. |
| __Плановый расчёт__ | Если данных достаточно и результат значим, воркер сохраняет автоматический шаблон в историю. Для одинакового снимка такой отчёт сохраняется один раз. |

Чтобы получить результат LLM-запроса, вызовите `GET /reports` с тем же
префиксом и найдите запись по ID из ответа `POST`.

| __Статус__ | __Что означает__ |
|---|---|
| __`pending`__ | Задание ждёт завершения. `report_type` на этом этапе может содержать `template` по умолчанию. Beat ставит задачу обработки ожидающих отчётов каждую минуту. |
| __`completed`__ | Текст доступен в `report_content`. `report_type: llm` означает ответ модели. `report_type: template` с заполненным `fallback_reason` означает подстановку шаблона. |
| __`failed`__ | Например, старое задание без входного снимка завершается с `fallback_reason: missing_snapshot`. |

Шаблон подставляется при отсутствии ключа (`missing_key`), ошибке запроса
или формата ответа провайдера (`provider_error`), а также если ответ обрезан,
пуст или провайдер указал причину завершения, отличную от `stop`
(`incomplete_response`). В этих случаях задание завершается со статусом
`completed`, а результат доступен даже при недоступности LLM.

Модель получает сводку метрик и может пояснить результат и предложить
дальнейшие действия. Статистику рассчитывает сервис. Клиент LLM ожидает
совместимый контракт Chat Completions, в том числе параметр
`max_completion_tokens` и текст в `choices[0].message.content`. Работу с
Atria-Dawn проверяли вживую. Для другого провайдера нужно сверить контракт,
а при несовместимом формате адаптировать клиент.
