# Feature-флаги

Флаг управляет доступностью функции для конкретного пользователя. Обычный флаг
позволяет включить функцию для выбранной аудитории, а A/B-флаг распределяет
подходящих пользователей между вариантами эксперимента.

## Типы и жизненный цикл

| __Тип__                               | __Как принимается решение__                                                                                             |
|---------------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| __`simple`, `boolean`, `percentage`__ | Используют одну логику. После таргетинга доступность определяется `rollout_percentage`.                                 |
| __`ab`, `ab_test`__                   | После таргетинга назначают вариант запущенного эксперимента по весам. `rollout_percentage` в этой ветке не применяется. |

При создании флаг по умолчанию выключен (`enabled: false`). У обычного флага
rollout по умолчанию составляет `100`, поэтому после включения он доступен всей
аудитории, прошедшей таргетинг. Изменить `enabled` можно через
`PATCH /api/flags/{key}`. Отключение обратимо и сохраняет конфигурацию флага.

`DELETE /api/flags/{key}` выполняет мягкое удаление. Флаг исчезает из обычных
запросов и `/resolve`, его ключ остаётся занятым, история экспериментов сохраняется.
Пока эксперимент `running` или `paused`, API возвращает `409` при попытке
переименовать или удалить флаг, добавить или удалить вариант либо изменить ключ
или вес существующего варианта. Отключение флага прекращает выдачу назначений,
при этом статус эксперимента управляется отдельно.

## Как работает `/resolve`

Передайте `flag_key`, стабильный клиентский `user_id` и при необходимости
`attributes`. Порядок проверок определяет причину в ответе.

| __Шаг__                         | __Результат__                                                                                                                                                                                |
|---------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| __1. Поиск флага__              | Если флаг с таким ключом не найден или удалён, API возвращает `404`.                                                                                                                         |
| __2. Проверка `enabled`__       | Выключенный флаг даёт `enabled: false` и `reason: disabled`.                                                                                                                                 |
| __3. Таргетинг__                | Если хотя бы одно активное правило не выполнено, результат содержит `enabled: false` и `reason: targeting`.                                                                                  |
| __4. Rollout обычного флага__   | Возвращается `reason: rollout`, а `enabled` зависит от корзины пользователя.                                                                                                                 |
| __4. Назначение A/B-варианта__  | При успехе ответ содержит `enabled: true`, `reason: ab_test`, `variant` и `experiment_id`. Без запущенного эксперимента причина будет `no_active_experiment`, без вариантов — `no_variants`. |

Некорректная конфигурация, например неизвестный тип или единственный вариант
у запущенного A/B-эксперимента, даёт `409`. Для A/B-назначения используйте
`variant` и `experiment_id`. Когда назначения нет, оба поля равны `null`, а
совместимое поле `variant_key` имеет значение по умолчанию `control`.

Успешное A/B-назначение записывает `impression` в MongoDB до ответа. Если запись
не удалась, API возвращает `503`. Повторный вызов `/resolve` для того же
пользователя может записать ещё один показ. При расчёте статистики участник
учитывается один раз. Подробнее о событиях и расчёте — в [руководстве по
экспериментам](experiments.md).

## Таргетинг по атрибутам

Правила одного флага соединяются логическим И. Учитываются только правила
с `is_enabled: true`. Если таких правил нет, этап таргетинга пройден.

| __Операторы__                | __Как проверяются значения__                           |
|------------------------------|--------------------------------------------------------|
| __`eq`, `ne`__               | Проверяют равенство или неравенство с одним значением. |
| __`in`, `not_in`__           | Проверяют вхождение или невхождение в непустой список. |
| __`gt`, `gte`, `lt`, `lte`__ | Сравнивают атрибут с одним числом.                     |

Атрибут может быть строкой, числом или логическим значением. Строка `"18"`
не подходит для числового правила `gte` с порогом `18`. Логическое `true`
отличается от числа `1`. Отсутствующее значение, `null`, массив или объект
не проходят правило даже с оператором `ne` или `not_in`.

Добавьте правило через `POST /api/flags/checkout-v2/targeting` с токеном владельца
с правом записи или администратора. Такое правило допускает пользователей,
у которых `country` равен `RU` или `KZ`.

```json
{
  "attribute":"country",
  "operator":"in",
  "values":["RU","KZ"]
}
```

## Rollout и выбор варианта

Для обычного флага хеш SHA-256 от `user_id`, ключа флага и `salt` определяет
корзину от `0` до `99`. Флаг доступен, если корзина строго меньше
`rollout_percentage`. При `0` никто не проходит этот этап, при `100` проходят все.
Если повысить rollout с `25` до `50` при неизменных входах хеша, корзины `0–24`
останутся включёнными и к ним добавятся `25–49`.

В A/B-ветке хеш использует UUID эксперимента вместо ключа флага. Варианты
сортируются по `variant_key`, их веса задают накопительные границы корзин.
При весах `A=1`, `B=3` корзины `0–24` относятся к `A`, а `25–99` — к `B`.
Доли задают распределение корзин. Число участников в каждой группе зависит
от фактически пришедших пользователей. При неизменных входах хеша и весах
назначение повторяется. Смена `salt` или запуск другого эксперимента могут
изменить вариант для того же `user_id`.

## Пример решения

Для включённого флага `checkout-v2` задайте тип `percentage`, `salt: demo`,
rollout `25` и правило по стране из примера выше. Отправьте запрос `POST /resolve`.

```json
{
  "flag_key":"checkout-v2",
  "user_id":"customer-44",
  "attributes":{"country":"RU"}
}
```

| __Запрос__                       | __Ответ и причина__                                                                                  |
|----------------------------------|------------------------------------------------------------------------------------------------------|
| __`customer-44`, `country: RU`__ | `enabled: true`, `reason: rollout`. Страна подходит, корзина `12` входит в rollout.                  |
| __`customer-43`, `country: RU`__ | `enabled: false`, `reason: rollout`. Страна подходит, но корзина `45` находится за границей rollout. |
| __`customer-44`, `country: FR`__ | `enabled: false`, `reason: targeting`. Проверка завершается до вычисления корзины.                   |

Для примера A/B возьмём флаг того же имени с типом `ab`, тем же таргетингом
и `salt: demo`. Если UUID запущенного эксперимента равен
`11111111-1111-4111-8111-111111111111`, а веса `A=1`, `B=3`, запрос для
`customer-44` из `RU` даст корзину `97` и вариант `B`. С `country: FR`
этот же пользователь получит `reason: targeting` и `variant: null`.
При создании эксперимента API выдаёт собственный UUID. Поэтому в
[воспроизводимом демо](demo.md) ожидаемый вариант берётся из ответа `/resolve`.

Маршруты настройки флагов, вариантов и правил собраны в [руководстве по API](api.md).
