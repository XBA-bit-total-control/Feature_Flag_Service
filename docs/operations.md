# Эксплуатация сервиса

Команды выполняются в PowerShell 7 из корня репозитория.

Первичная настройка описана в [руководстве по запуску](getting-started.md).

Для minikube используйте [инструкцию Kubernetes](../k8s/README.md) с манифестами, порядком запуска и пробросом порта API.

## Проверка состояния

```powershell
docker compose ps -a
docker compose logs --tail 100 init api worker beat
$api = 'http://127.0.0.1:8000'
$ready = Invoke-WebRequest -Uri "$api/api/health/ready" -SkipHttpErrorCheck
"HTTP $($ready.StatusCode)"
$ready.Content
docker compose exec -T api python -m src.celery_app
```

Подставьте порт из `API_HOST_PORT` в `$api`, если изменили его.
`-SkipHttpErrorCheck` позволяет вывести статус и тело даже при ответе `503`.
Для `init` ожидается
`Exited (0)`, для API — `healthy`, для worker и Beat — `Up`.

| __Проверка__                                    | __Что показывает__                                                                                                                                                          |
|-------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| __`GET /api/health/live`__                      | API отвечает. Возвращает `200` с `status: ok` без обращения к БД.                                                                                                           |
| __`GET /api/health/ready` и `GET /api/health`__ | API проверяет PostgreSQL через `SELECT 1` и MongoDB через `ping`. Если обе БД доступны, ответ `200`. Иначе ответ `503` и `unavailable` у проблемной зависимости в `checks`. |
| __`python -m src.celery_app`__                  | Отправляет `events.ping` в RabbitMQ и ждёт `pong` до 10 секунд. Проверяет обмен с воркером для очереди `events` и получение результата.                                     |

Readiness проверяет только две БД. Проверку брокера и воркера выполняйте
отдельно. Для плановых задач дополнительно проверьте логи Beat и worker.

## Очереди и расписание Celery

В Compose один worker слушает три очереди. Beat публикует плановые задачи,
а worker выполняет их.

| __Очередь__      | __Задача__                        | __Когда запускается__                                                                                                                       |
|------------------|-----------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| __`events`__     | `events.process_pending`          | После успешного сохранения событий через API, включая показ при A/B-назначении. До 1000 документов за задачу.                               |
| __`events`__     | `events.cleanup_old`              | Каждые 24 часа. Удаляет старые события по [правилам хранения](data-model.md) и сохраняет компактное состояние участников при необходимости. |
| __`analytics`__  | `analytics.calculate_statistics`  | Каждые 30 минут. Пересчитывает запущенные эксперименты и сохраняет шаблонный отчёт при достаточных данных и значимом результате.            |
| __`reports`__    | `reports.generate`                | После создания нового задания через `POST /api/experiments/{experiment_id}/llm/reports`. Обрабатывает один ID.                              |
| __`reports`__    | `reports.process_pending`         | Каждую минуту. Подбирает до 100 самых старых ожидающих отчётов, в том числе после сбоя публикации.                                          |

Расписание задано интервалами в `src/celery_app.py`. Запускайте один экземпляр
Beat для этого расписания, чтобы избежать повторной публикации плановых задач.
Успешная обработка `events.process_pending` выставляет `processed: true` и
`processed_at`. Аналитика читает сохранённые события независимо от `processed`.

### Повторы и накопившиеся события:

- `events.process_pending` повторяется при сбое подключения к MongoDB.
  `events.cleanup_old` и `analytics.calculate_statistics` повторяются при
  ошибках подключения к MongoDB или операционных ошибках PostgreSQL.
  Для `reports.generate` повтор настроен при операционной ошибке PostgreSQL.
  Лимит каждой задачи — три повтора после первой попытки с увеличением задержки.
- `reports.process_pending` снова запускается на следующем тике Beat. Повторы
  HTTP-вызова LLM настраиваются отдельно через `LLM_MAX_RETRIES`. Если отчёт
  готов с `report_type: template`, проверьте `fallback_reason` в истории.
- При сбое публикации события остаются в MongoDB. Следующий приём событий
  может запустить обработку накопившихся записей. В расписании Beat отдельного
  периодического запуска `events.process_pending` нет.

После восстановления брокера можно поставить обработку событий вручную.
Повторяйте команду, пока показатель `feature_flags_events_pending` не снизится
до ожидаемого уровня. Для подбора отчётов вручную используйте вторую команду.
Она может вызвать внешний LLM API, если настроен ключ и есть ожидающие задания.
Команды выводят ID поставленных задач. Завершение проверяйте по логам, метрикам
и истории отчётов.

```console
docker compose exec -T api celery -A src.celery_app:app call --queue events events.process_pending
docker compose exec -T api celery -A src.celery_app:app call --queue reports reports.process_pending
```

## Метрики и логи

`GET /api/metrics` возвращает текст в формате Prometheus. Маршрут скрыт из
OpenAPI. Для чтения используйте `$api` из проверки состояния.

```powershell
Invoke-RestMethod -Uri "$api/api/metrics"
```

| __Метрика__                                 | __Как читать__                                                                                                       |
|---------------------------------------------|----------------------------------------------------------------------------------------------------------------------|
| __`feature_flags_resolve_requests_total`__  | Счётчик обработанных `POST /resolve` в текущем процессе API, включая ошибочные ответы. Сбрасывается при перезапуске. |
| __`feature_flags_events_pending`__          | Текущее число документов с `processed: false` в MongoDB.                                                             |
| __`feature_flags_llm_fallback_reports`__    | Текущее число завершённых отчётов с заполненным `fallback_reason` в PostgreSQL.                                      |

Если чтение одной из БД завершилось ошибкой, соответствующая метрика
отсутствует в ответе. Отсутствие строки отличается от значения `0`.

```console
docker compose logs --tail 100 -f api worker beat
```

В логах приложения `http.request` содержит метод, шаблон маршрута, имя
обработчика, HTTP-статус и время выполнения в миллисекундах. При сбое
публикации задачи обработки событий API пишет `events.publish_failed`.
При подстановке шаблона воркер пишет `reports.llm_fallback` с полем `reason`.
Уровень логов приложения задаётся через `LOG_LEVEL`.

## Диагностика типовых сбоев

| __Симптом__                                                    | __Что проверить__                                                                                                                                                                                                    |
|----------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| __API не запускается, `init` завершился с ошибкой__            | Выполните `docker compose logs init`. Проверьте доступность БД и ошибку Alembic или создания индексов. После устранения причины повторите запуск по руководству.                                                     |
| __Readiness возвращает `503`__                                 | Найдите проблемную БД в `checks`. Проверьте `docker compose ps` и логи `postgres` или `mongo`. При прямом запуске Python сверьте хосты и порты из его окружения.                                                     |
| __Worker не отвечает или растёт число необработанных событий__ | Проверьте логи `rabbitmq` и `worker`, затем очередь `events` и число её потребителей. После восстановления брокера отправьте задачу обработки накопившихся событий.                                                  |
| __Отчёт долго остаётся `pending`__                             | Проверьте, что worker слушает `reports`, а Beat отправляет `reports.process_pending`. Сверьте состояние отчёта через `GET /api/experiments/{experiment_id}/reports`.                                                 |
| __Вместо LLM-текста получен шаблон__                           | Проверьте `fallback_reason`. Для `missing_key` проверьте окружение worker. Для `provider_error` проверьте адрес, модель и доступность API. Для `incomplete_response` проверьте причину завершения и лимит генерации. |
| __Снимок результатов не обновляется__                          | Проверьте статус эксперимента, очередь `analytics` и логи Beat и worker. Плановый расчёт выбирает только `running`. Для `running` и `paused` можно запустить ручной пересчёт через API.                              |

Чтобы различить ожидающие сообщения, сообщения в работе и очереди без
потребителей, запросите состояние очередей напрямую в RabbitMQ.

```console
docker compose exec -T rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

Для проверки всей цепочки от HTTP до отчёта используйте [демо](demo.md).
